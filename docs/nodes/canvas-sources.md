# Canvas sources

Raw source nodes turn browser events on the performance canvas into events and signals. They don't interpret anything; [gesture recognizers](gesture-recognizers.md) sit on top. Design: "Canvas event sources".

| Node | Browser events | Outputs | Milestone |
| --- | --- | --- | --- |
| Pointer | pointerdown, pointermove, pointerup, pointercancel, pointerenter, pointerleave | Down, Move, Up, Cancel events per channel, and All: every event tagged with its `phase` ([ADR 0028](../decisions/0028-recognizers-pass-claim-cancel.md)), plus `phase: 'leave'` when a hovering pointer leaves; X, Y, Pressure, Speed signals per channel; Count of active pointers | M1 (basic), M2 (complete) |
| Pointer (high rate) | `getCoalescedEvents()` on pointermove (not `pointerrawupdate`, see Coalesced samples) | Every sub-frame move sample, for smooth strokes and fast flicks, with Pointer's Down, Up and Cancel; All | M2 |
| Click | click, dblclick, auxclick, contextmenu | Click, Double, Middle, Right events with position | M2 |
| Wheel | wheel (including macOS trackpad pinch, sent as wheel + ctrlKey) | DeltaX, DeltaY, Zoom events; accumulated X/Y/Zoom signals with a decay knob | M2 |
| Pen | Pointer events filtered to `pointerType: pen` | Tilt X/Y, Altitude, Azimuth, Twist, Tangential pressure, Barrel button; Down, Move, Up, Cancel and All like Pointer | M2 |
| Touch extras | Touch contact size; Safari `gesturechange` | Contact width/height; native Scale and Rotation (Safari only) | M2 |
| Key | keydown, keyup while the canvas has focus | Down/Up events with `key`, `code`, `repeat`, one channel per `code`; All (no repeats); a Held signal for each chosen key; a Keyboard → Note mode (two-row piano layout) | M2 |
| Canvas | resize, focus, blur, visibilitychange | Size signals and Focus/Blur/Hidden/Visible events, so patches can fade or pause cleanly | M2 |
| MIDI In | Web MIDI note and CC messages | Note at each note-on, with a **Length** knob for its duration; Note On and Note Off events with pitch and velocity; a CC signal for one CC number; all per MIDI channel (channel = MIDI channel + 1) and filtered by a **Channel** menu (All, 1–16); a raw MIDI output with every channel message, which the Channel menu doesn't filter | M2 ([ADR 0004](../decisions/0004-web-midi-in-v1.md)) |

Later, each behind a permission and not in v1: Gamepad (buttons and axes, polled each frame), Device motion and orientation, Microphone (level, onset, pitch).

## Event payload

Every pointer event (Pointer, Pointer (high rate), Pen and Touch extras' sizes) carries these base fields, so any node can read them through Get Field. Click, Wheel, Key, Canvas, Touch extras' Gesture and MIDI events carry `time` and `channel` and the fields their paragraphs below list.

| Field | Meaning |
| --- | --- |
| `time` | Audio-clock time the event is scheduled at |
| `channel` | Stable id for this pointer, touch or key for the life of the contact: for pointers, a slot (below) |
| `x`, `y` | Canvas position, normalized 0–1, with y = 0 at the top (the fluid's convention) |
| `dx`, `dy`, `speed`, `angle` | Motion since the previous sample for this channel, in canvas units per second |
| `pressure`, `width`, `height` | Contact force and size, where the hardware reports them (mouse: 0.5 while pressed) |
| `pointerType` | mouse, touch or pen |
| `button`, `buttons` | Which buttons changed, and which are held |
| `shift`, `alt`, `ctrl`, `meta` | Modifier keys held |
| `age` | Seconds since this channel's down event |
| `coalesced` | On a pointermove sample from `getCoalescedEvents()`: Pointer (high rate) reads these, Pointer the plain moves |
| `interval` | Seconds since this pointer's previous sample, from the browser's `timeStamp`s (left out on its first sample, and on its first since each up, cancel or leave, a hover move included). Motion is measured over it |

`dx` and `dy` are velocity components; `angle` is atan2(dy, dx) in radians (0 to the right, π/2 down) and holds its last value while the pointer is still. A channel's first sample after it's taken has no motion, and `age` is 0 on a hover move.

**Coalesced samples.** A browser's coalesced list for a pointermove includes the dispatched move itself. So the host pushes every sample of the list as `pointermove` with `coalesced: true`, and then the plain move. Pointer (high rate) reads only the samples and Pointer only the plain moves, so neither sees a sample twice. The samples and the move go in one push, at one stamp (stamps can't go back before currentTime). Every pointer event the host sends (down, move, sample, up, cancel) carries `interval` (except a pointer's first; see the table): the seconds since that pointer's previous sample by the browser's clock, and motion is measured over it: stamps carry render quanta and handler delays (a late handler would squeeze two frames' samples together), so the nodes fall back to stamps only for events without one. The host takes samples from `getCoalescedEvents()` on pointermove in every browser, not from `pointerrawupdate`: rawupdate's samples come again in the next move's list, and a push per sample would cost a rewind each and collide on render-quantum stamps. Samples closer than 1 ms add up before motion is measured, so bursts can't make the speed spike. Each sample costs two events (Move and All), so in a 120 ms limit window that fills up the pointer sources stop emitting moves before the per-node cap and keep a reserve for Down, Up and Cancel. The patch-wide cap (2,048 events) counts every node, so in a busy patch it can still drop them.

**Pointer slots.** Pointer sources number contacts by slot, not by raw `pointerId`. A pointer takes the lowest free slot from 1 on its first event (pointerenter or a hover move included) and frees it on pointerup, pointercancel or pointerleave (a leave while down waits for the up). An up or cancel with no contact down for its pointer (pressed outside the canvas, then released inside) is dropped and takes no slot. At one time stamp, a pointer that lifts frees its slot before another pointer takes one. The map is node state, so live and replay give the same channels; input streams keep recording raw pointerIds. Channel 0 reads the most recent pointer. Past 16 slots, the pointer that changed least recently gives its slot up (a hover first), with a Cancel if it was down.

**Click.** The host pushes each click, dblclick, auxclick and contextmenu once as `{ x, y, pointerType, button, buttons, shift, alt, ctrl, meta }`, with no channel, so clicks come on channel 0; where the browser's event has no `pointerType` at all (Safari's are plain mouse events), it's that of the last pointerdown on the canvas from any pointer, or `mouse` before the first, so with a mouse and a finger on the canvas at once a click can take the other's type (Safari's click carries no pointerId to tell them apart). A keyboard contextmenu (the menu key, or Shift+F10 on the focused canvas) has an empty `pointerType` in Chromium and reports `mouse`, at whatever position the browser gives it. Click is each `click` (the primary button's, a tap's too), so a double click is two Clicks, then a Double from the `dblclick`. Middle is an `auxclick` with button 1; the auxclicks browsers send for the right, back and forward buttons are dropped, so a right-click is Right only. Right is each `contextmenu`: a right-click, Ctrl-click on macOS, a long press on touch, or the menu key. Click rewrites its pushes so x and y clamp to 0–1. While a patch reads contextmenu, the canvas suppresses the context menu; while it reads auxclick, it blocks a middle press's default (autoscroll, or paste on Linux), which would swallow the auxclick. Not a contact source: no All.

**Wheel.** The host pushes each wheel event once as `{ x, y, deltaX, deltaY, deltaMode, shift, alt, ctrl, meta }`, with the deltas and deltaMode as the browser reports them, and no channel. Wheel converts the deltas to CSS pixels (a line is 40 px, a page 800 px) and drops `deltaMode`. A wheel with Ctrl (a trackpad pinch in Chrome, Edge and Firefox, or Ctrl + wheel) goes to Zoom only, with `zoom` = −deltaY / 100, positive zooming in; the others go to DeltaX and DeltaY where that delta isn't 0. Scroll X, Scroll Y and Zoom level sum deltaX / 100, deltaY / 100 and `zoom`, so a Chrome mouse notch adds about 1, and decay toward 0 as e^(−Decay × seconds since the last wheel); Decay 0 holds them. While a patch reads wheel, the canvas keeps it from scrolling or zooming the page; wheels before audio starts are dropped.

**Pen.** On a pen's pointer events (enter, down, move, up, cancel, leave, and the coalesced samples) the host adds `tiltX` and `tiltY` (degrees, −90 to 90, toward +x and toward the user), `twist` (degrees, 0 to 359) and `tangentialPressure` (−1 to 1), and `altitudeAngle` (radians, 0 lying flat to π/2 upright) and `azimuthAngle` (radians, 0 to 2π from +x) where the browser has them; other pointers leave them out. The barrel button is `buttons` bit 2, so it has no field. Pen reads what Pointer reads where `pointerType` is `pen`, with its own slots (the first pen is slot 1 whatever Pointer gave it), and completes each event: missing altitude and azimuth come from tilt and missing tilt from them, as the Pointer Events spec converts them (a pen upright when there's neither); tilt, altitude and tangential pressure clamp to range, azimuth and twist wrap; `barrel` is 1 while bit 2 is held. Its Tilt X, Tilt Y, Altitude, Azimuth and Twist signals hold the slot's last values after Up or a leave, as X and Y do; Tangential pressure and Barrel button read 0 once the slot is free. Before any pen, and on a slot a pen has only entered (no down or move yet), they read a pen held upright, not the previous pen's values. The barrel follows the browser: pressed in the air it's the first button, so a pointerdown with `button` 2 and the hover's pressure, and Pen and Pointer both emit a Down for it (Chromium on Windows Ink may also send a contextmenu); pressed while the tip is down, or the tip touching while it's held, it's a pointermove with `buttons` 3. A patch that wants tip contacts only filters on `button` or `pressure`.

**Touch extras.** Contact size comes from the pointer events' `width` and `height` (CSS pixels, as the browser reports them), which the host already sends on every pointer event. Touch extras reads what Pointer reads where `pointerType` is `touch`, with its own slots as Pen keeps them (the first finger is slot 1 here whatever Pointer gave it; with only fingers on the canvas the two agree). Its Width and Height signals are the slot's latest size, clamped to 0–1,000 px, and read 0 once the finger lifts, before any touch, and on a slot taken by an enter alone until that touch's first down or move. A browser with no contact geometry reports 1 × 1 (the Pointer Events spec's default), so they read 1 there; only a hand-written stream can leave a size out, and a missing or non-finite one reads 0. Safari sends a pinch or twist (two fingers on iOS, the trackpad on macOS) as gesturestart, gesturechange and gestureend; the host pushes each `gesturechange` once as `{ x, y, scale, rotation, shift, alt, ctrl, meta }` (x and y where it has the gesture's centre), with no channel: `scale` is the ratio since gesturestart (1 at the start) and `rotation` the degrees since gesturestart, positive clockwise, both as Safari reports them. Touch extras' Gesture output emits each on channel 0 with `rotation` in radians (as Pinch's) and `scale` clamped to 0.001–1,000; a scale that isn't above 0, or a rotation that isn't finite, keeps the previous value. Its Scale and Rotation signals, the same on every channel, hold the latest gesturechange's values. gesturestart and gestureend aren't stream types, so after a gesture ends they hold its last values until the next gesture's first change, which starts near 1 and 0 again: Safari's scale and rotation are per gesture, not running totals, so a patch mapping Scale or Rotation to a param jumps back at the start of every new pinch (one that ends at 2 drops Scale to about 1 when the next begins). **Outside Safari** there is no gesturechange: Gesture never fires and Scale and Rotation read 1 and 0 (Chrome, Edge and Firefox send a trackpad pinch as wheel + ctrlKey, Wheel's Zoom; on touch screens use Pinch). While a patch reads gesturechange, the canvas keeps gesturestart, gesturechange and gestureend from zooming the page; gestures before audio starts are dropped. Not a contact source: no All.

**Hover end.** When a pointer that isn't down gives its slot up (a pointerleave, or eviction past 16 slots), All carries a `phase: 'leave'` event on its slot, at the slot's last position, with no motion and `age` 0. A pointer with no Down, Move, Up or Cancel since it took the slot (an enter, then a leave or eviction) gets none; moves the event budget thinned still count. It's not a contact phase: it has no per-phase port, opens and ends no contact, and recognizers pass it on Pass alone (ADR 0028, amended for #101). Dwell drops the slot's stay on it, so a pointer that leaves still doesn't dwell at the edge, and the slot's next pointer starts afresh. It's never thinned by the event budget.

## Rules for this family

- **Timing.** Input events are stamped `ctx.currentTime + 5 ms` and take the immediate path ([ADR 0008](../decisions/0008-one-clock-window-queries.md), [ADR 0017](../decisions/0017-immediate-offset-and-catch-up.md)).
- **The host delivers events.** The engine doesn't touch the DOM. It receives canvas events from the host ([ADR 0013](../decisions/0013-engine-editor-split.md)), and the DOM listener code lives outside `packages/engine`.
- **Platform rules the runtime handles:**
  - The canvas sets `touch-action: none` and takes pointer capture on down.
  - The context menu is suppressed only when a patch uses right-click.
  - The first pointerdown also unlocks the AudioContext and is still delivered, so it makes a sound. So does a keydown on the focused canvas (not a repeat, Escape, Tab or a lone modifier): a key press is a user gesture.
- **Focus.** In Play view the canvas has keyboard focus. In Patch view, keys go to the editor unless the preview canvas is focused. Escape always returns to the editor.
- **Keys.** The host pushes each keydown and keyup on the focused canvas as `{ key, code, repeat, shift, alt, ctrl, meta }`, with no `channel`: the code is the key's id. Escape is never sent. Key's events stay with the canvas (keydown doesn't reach the editor's shortcuts); keyup still bubbles, since React Flow tracks held keys from it. With a Key in the patch, keydown's page default is prevented, apart from Tab, the function keys (F1–F24) and Ctrl or Meta shortcuts. While audio isn't running, auto-repeats are dropped and the rest are held, like a pointerdown.
  - **Channels.** A key's channel is fixed by its `code`, not by press order, so live and replay agree: its place in Key's `KEY_CODES` list from 1 (KeyA–KeyZ 1–26, Digit0–Digit9 27–36, then punctuation, Space 51, editing keys, modifiers, navigation, F1–F24 and the numpad). The list is append-only. A code it doesn't list gets a hash of it in 1000–9999.
  - **Repeats** reach Down with `repeat: true` and never All, Note or Held. A keyup for a key that isn't down is dropped; a keydown (not a repeat) on a key already down ends it with an Up first. At one stamp (pushes held for the audio start share one), a key's keydowns and keyups alternate from its state there, so a tap and a re-press before audio starts leave it down. Down and Up carry `age`, seconds since the key's keydown.
  - **Lost keyups.** The canvas gets no keyup once it loses focus, so on every platform the host sends a keyup for every key still down when the canvas blurs (before Canvas's Blur). macOS also sends none for keys released while Cmd is held, so there (and on iPadOS) Meta's keyup also releases every key still down but the modifiers: on macOS a key held across a Cmd tap is cut short. They're recorded like any keyup.
  - **Held** reads 1 while a key named in Held keys (codes, separated by spaces or commas; default Space) is down. Any well-formed code is accepted, including ones Key puts on hashed channels; Escape isn't, since it's never sent. Channel 0 reads whether any of them is; a key's channel reads that key. Empty, every key counts.
  - **Keyboard → Note** plays the tracker's two-row piano, by code: Z S X D C V G B H N J M , L . ; / from the Octave knob's C (Octave 3: Z is C3, MIDI 48), and Q 2 W 3 E R 5 T 6 Y 7 U I 9 O 0 P [ = ] an octave up (Q is C4). Notes come at keydown, with the Velocity and Length knobs; repeats never retrigger, and a keyup ends nothing.
- **Canvas.** The host pushes the canvas's size as `resize` with `canvasWidth` and `canvasHeight` in CSS pixels, its keyboard focus as `focus` and `blur`, and the page's visibility as `visibilitychange` with `visibility` `'hidden'` or `'visible'` (`document.visibilityState`), all on channel 0. Canvas's Width and Height read the latest size in CSS pixels (0 before the first) and Aspect width / height (1 while either is 0); Focus, Blur, Hidden and Visible come at the pushes' times, without the payload.
  - **While audio is stopped** the four are dropped, not held: dragging the pane or tabbing about before the first tap would pile them up. The host keeps the canvas's state and, when audio starts, sends the size and any focus or visibility that differs from what the sources last got. So the first tap, which focuses the canvas, brings the size and a Focus.
  - **Changes only.** The host sends a focus, blur or visibility change only when it happens, so Canvas doesn't drop repeats; a stream that repeats one gets the event again.
  - **Hidden doesn't touch audio.** The AudioContext keeps running while the page is hidden (the scheduler only lengthens its lookahead); a patch that should fade or pause does it from Hidden and Visible.
  - **A Canvas added while playing** gets the size once its swap lands: a swap takes effect at a window boundary at least `SWAP_MARGIN` past now (ADR 0023), and a size pushed before that would reach a window the new node isn't in yet.
- **Permissions.** Sources that need permission (MIDI, later motion and mic) ask only when a patch containing them first plays. If denied, they show a blocked state on the node.
- **MIDI.** The host pushes each MIDI channel message as `{ type: 'midi', status, data1, data2 }`: the status byte and the data bytes as numbers, with no `channel` (so channel 0), so the MIDI channel is in `status`. Two-byte messages (program change, channel pressure) have no `data2`. The host drops system messages (sysex, clock, active sensing) and malformed bytes, so neither recordings nor the raw MIDI output carry them. MIDI events arriving while audio isn't running are dropped, not held: MIDI never starts audio. The raw MIDI output passes every channel message unchanged, whatever the Channel menu says. MIDI In decodes note-on, note-off and CC from it; velocity is 0–1 (data2 / 127), and a note-on with velocity 0 counts as a note-off. Notes carry their own duration ([ADR 0028](../decisions/0028-recognizers-pass-claim-cancel.md)), so MIDI In's Note comes at note-on with the Length knob's duration, and a note-off ends nothing; patches that need the off read Note Off. The CC signal holds the chosen controller's latest value (data2 / 127) per MIDI channel, and channel 0 reads the latest on any.
- **Recordings.** Every event a source emits must be replayable from an input stream ([ADR 0029](../decisions/0029-input-stream-format.md)), so recordings reproduce performances.
