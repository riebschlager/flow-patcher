# 0031 · Audio instances automate per chunk and take knob edits in place

Status: Proposed · 2026-10-23 · Amends [0023](0023-hot-swap-reruns-from-next-boundary.md)

## Context
The runtime calls an audio instance only through `schedule()`, and only when the node got Event or Note input in the chunk. A node with only an Audio input (Filter, Gain, Pan, Mixer in #88; Reverb ★, Delay ★ in #81) is never called again after `audio()` builds it, so a Signal cable into its params never reaches Web Audio. ADR 0023 rebuilds an audio node whose params changed, so a knob edit swaps in a new Web Audio graph and jumps. effects-mix.md requires that modulated params ramp and never jump. Chris asked for knob edits to update params in place (2026-10-23).

## Decision
- **A per-chunk hook.** `AudioInstance.automate?(t0, t1)` is called once per chunk the runtime emits, for every node with an audio instance, at its place in plan order, right after `schedule`. Its Signal sources have been queried for the chunk by then, so `param()` answers for [t0, t1). State-only replays (a rewind's stretch before its event) don't call it.
- **Audio-clock times.** The times are the ones `send()` would give events: a chunk that starts in a catch-up's missed stretch moves by the shift (ADR 0017), and t0 is never before the clock at hand-over. A chunk wholly behind the clock isn't automated. The shift goes by the chunk's start, where `send()` goes by each event's time, so in a chunk that straddles the end of the missed stretch, automation and notes disagree by up to the shift for that chunk. The shifted chunk overlaps the next one, and the next one's cancel at its own t0 takes over.
- **Idempotent re-runs.** A rewind (ADR 0019) or swap calls it again for chunks already covered, from the re-run's start. The node cancels what it scheduled from t0 on and schedules again. It samples on an absolute grid, t = k / 60 (`AUTOMATION_RATE`, `automationTimes`), so the timeline depends only on the grid points covered, not on window splits or re-runs. `automateParam(target, t0, t1, value)` does both steps.
- **Linear ramps between grid points.** Linear ramps, not `setTargetAtTime`, matching design.md's "60 Hz, interpolated for audio". node-web-audio-api 2.2.0, which headless runs use, evaluates a pending `setTargetAtTime` curve before its start time: gains of 10⁹ and more were measured until it began. design.md, effects-mix.md and nodes/README.md said `setTargetAtTime`; they now say "ramp, never jump" and point here.
- **`connected(name)`** on `AudioSetupContext`, so a node automates only cabled params. For params it is fixed for the instance's life, because a change to the cables into params still rebuilds. For Event, Signal and Value ports it answers for the plan running the chunk, so it can change across a swap, or a rewind across one. Audio ports always answer false.
- **In-place knob edits.** A definition lists in `liveParams` the params it can change on a running instance. When a swap changes only those params, and the instance has `update(params, time)`, the runtime keeps the instance and calls `update` with the new params. `time` is the swap time, clamped to the clock. The node ramps unmodulated params from there with an `editRamp` per param: hold the value until `time`, then a 20 ms linear ramp. An edit that lands during the previous ramp continues that ramp to the point it has reached, then turns, so it never steps. Modulated ones need nothing extra: the node is still "changed", so the swap re-runs the windows from `time`, and `automate`'s `param()`, which reads the plan running the chunk, adds the modulation to the new base. `SwapReport.updated` lists these nodes. A swap still rebuilds as in 0023 when anything else changes: a param not in `liveParams` (a menu that changes the graph), the type or version, the definition, the seed, or the cables into params. It also rebuilds when `keepState` resets the node (the instance holds the state object it was built with), and when the instance has no `update`.
- **Output opts in.** Output's `level` is in `liveParams`. `update` ramps the master gain, so a level edit no longer restarts the limiter (0023, Consequences). It is cheap: one gain param behind one `editRamp`. Level stays non-modulatable; modulation would be a separate change.

## Consequences
- Filter, Gain, Pan, Mixer, Reverb and Delay can follow cables and take knob turns without clicks. A modulated param has up to 1/60 s of control latency, linearly interpolated.
- A re-run cancels the linear ramp in progress at t0 and schedules it again in the same task. A browser that renders between the two calls could hold the previous value for one render quantum. Check this in #88's e2e run with a modulated Filter.
- Notes `schedule` already received keep the params they were sampled with. A node that needs them to follow an in-place edit does so itself in `update`.
- Every audio node is called once per chunk now, so the per-chunk cost grows by one call per audio node. Most do nothing.
