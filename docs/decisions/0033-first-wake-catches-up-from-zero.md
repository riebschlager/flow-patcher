# 0033 · The first wake catches up from 0, within the catch-up limit

Status: Accepted · 2026-10-25 · Amends [0017](0017-immediate-offset-and-catch-up.md), [0027](0027-immediate-notes-within-one-clock-step.md) · Amended 2026-10-25 for #97 (lateness classified by lead; caught-up events start at now + 5 ms)

## Context
In the editor the AudioContext stays suspended until the first tap, so the scheduler queries nothing before it. By the first running wake after the resume, `currentTime` has already moved a few ms past 0, and that wake started its window at `now`. An event at exactly t=0, such as a Clock's first tick, was never queried and never played (#105). Headless runs wake at exactly 0, so they never showed it.

The fix catches up [0, now) with 0017's mechanism. In the e2e that checks it, the catch-up then ran into 0027's rule that scheduled events are never late. A catch-up moves its stretch to start at the wake's `now`, with no lead. Before, only rare late wakes did that, but now nearly every cold start does it for the t=0 event. The first wake's query is often the slowest of a session (its code isn't warm yet, and it creates and starts the first Web Audio nodes; the audio instances themselves are built earlier, when the runtime attaches audio), so `currentTime` often steps during it. In 30 Chromium runs on macOS the step left the t=0 note behind the clock at hand-over in about one run in ten, and behind it at `start()` in a few more, by at most one step (5.3 ms).

## Decision
- The first running wake, the one before any window has been queried, treats 0 as its horizon. If `now` is within the catch-up limit (100 ms), it catches up [0, now): moved to start at `now` + 5 ms, keeping its spacing, as 0017 does (with the lead below). So a t=0 event sounds 5 ms after the resume. When the wake reads exactly 0 at a resume (the clock hadn't moved yet), it catches up [0, 0] the same way, so the t=0 event has the lead in every case; that isn't a late wake, so `catchUps` doesn't count it, but `caughtUp` counts its events. A run whose clock runs from the start (headless, tests) has no resume and nothing in flight during its first query, so its t=0 events stay at 0.
- Past the limit, the first wake starts at `now`, as before #105, and doesn't count a stall. A t=0 note is lost only after a startup slower than 100 ms. Nothing in [0, now) was ever heard, so a stall count would report a slow startup as a dropped window. 0017's no-burst rule holds for every catch-up, the first included: none is longer than the limit, even when something else queried part of [0, now) first.
- A resume after a suspend or `halt`, once a window has been queried, is unchanged: it carries on from the horizon, or from `now` if the clock has passed the horizon, and doesn't catch up.
- Held pushes, such as the first tap, are replayed after that wake's catch-up and stamped `currentTime + 5 ms`. The t=0 note goes first, and the tap's note follows at the same time or later: both have the 5 ms lead, and the push reads the clock after the wake did.
- A caught-up event that is still behind the clock at hand-over is moved to the clock, like any other late event. This applies to every catch-up, not just the first. It is counted in `lateCaughtUp`, not in `lateScheduled`, and `lateCaughtUpMaxMs` records the most such an event was behind the clock, as `lateImmediateMaxMs` does for a tap (0027). The runtime reads the clock at hand-over, clamps to that, and reads it again once the audio node's `schedule()` returns, since the node calls `start()` inside it; it counts against the later reading (#97), so a step between the two reads can't go uncounted. That makes each count an upper bound: it may include an event whose `start()` came before the step. This holds for all three counters. A caught-up event is late by design, and `caughtUp` already counts it. It may reach Web Audio up to one audio clock step behind `currentTime`, plus the wall time of its own wake's query and `schedule()` calls: the model 0027 uses for a tap's own note (one step plus the re-run). The scheduler records that duration for the wake that set `lateCaughtUpMaxMs` (`lateCaughtUpWakeMs`, on the main thread's clock), and the specs bound each worst case by its own wake. That isn't circular: the duration is the main thread's work, measured whatever the late event did, and the step comes from the platform and the audio thread (0027) (#97).
- **Caught-up events get the immediate offset as a lead (#97).** Every catch-up, the first wake's included, moves its missed stretch to start at the wake's `now` + `IMMEDIATE_OFFSET` (5 ms), the lead a tap's own note gets (0017), instead of at `now`. Handed over at `now` with no lead, a clock burst during the wake's query and `schedule()` made its first events late by the burst plus that work: on macOS Chromium the e2e edit run once had a caught-up event 16 ms behind the clock, with one step (the probe's largest burst, 0027) at 10.67 ms. With the lead, a burst up to 5 ms isn't late at all, and a longer one is late by 5 ms less. The cost: caught-up notes play 5 ms later than before, 5 ms after the wake rather than at it. The bound is one step plus the wake's own duration, as above.
- 0027's "scheduled events must never be late" now covers events queried ahead of the clock: `lateScheduled` stays 0.
- Lateness is classified by lead, not by path (#97). A scheduled event at or before the wake's `now` has no lead by construction, like a caught-up one: the first wake of a clock that runs from the start, at exactly 0 (nothing to catch up, so the t=0 event is in its ordinary window; at a resume that reads 0 it is caught up instead, as above), or a window that starts at `now` after a resume or a stall. Behind the clock, it counts in `lateCaughtUp`, with the same one-step bound. Only events queried after `now` count in `lateScheduled`. A push's events count in `lateImmediate` as before. On macOS Chromium the first wake read exactly 0 in about one run in twenty at first, and in 17 of 20 runs once the output ran at 44.1 kHz; its t=0 note's `start()` then came one step (5.3–5.8 ms) after the hand-over's read, which is why such a resume now catches up [0, 0] with the lead.
- The M1 gate box **No late events** (milestones.md) reads with that split. Over the e2e edit run, no event queried ahead is handed to Web Audio before `currentTime` (`lateScheduled` is 0). A tap's own note is at most one audio clock step late (`lateImmediateMaxMs`), and a caught-up event at most one step plus its wake's query and `schedule()` (`lateCaughtUpMaxMs` against one step plus `lateCaughtUpWakeMs`). The edit run asserts all three. The box's wording stays as it is.

## Consequences
- The first note of a patch sounds at the first tap instead of one period later, unless startup took more than 100 ms. The event log keeps the patch's own times, the same as a clock that started at 0. Headless runs and the golden logs don't change.
- As with any catch-up, [0, now), moved to [now + 5 ms, 2·now + 5 ms), overlaps the ordinary window from `now` by up to 100 ms, once: a flam at most.
- Visual nodes see caught-up events at their own times (design.md, Lifetimes), so the t=0 splash can lead its sound by the catch-up plus its 5 ms lead, at most 105 ms.
- Signal automation in the first chunk moves by the shift, like any catch-up chunk (0031).
- `RuntimeCounters.lateCaughtUp` and `lateCaughtUpMaxMs` are new. The first-note e2e and the e2e edit run both bound `lateCaughtUpMaxMs` by one clock step plus `lateCaughtUpWakeMs`, the duration of the wake that set it (#97). Locally (macOS Chromium, 44.1 kHz) the wake that set it ran 2.4–3.7 ms; the worst caught-up events were 6.61 ms late (an 11.61 ms jump less the lead) against a 5.80 ms step, within one step plus that wake.
